# Engineering Review — October 2026

A critical look at DiceWatcher as of commit `ffc0141` ("successfully identifying pips on a white d6"). The rewritten plan that follows from this review is in [project-spec.md](./project-spec.md).

## Summary

The repo is a clean, building pnpm monorepo (`pnpm install && pnpm typecheck && pnpm build` all pass) with a working same-machine demo: a Foundry module opens the web app as a popup, the web app captures a frame, a hand-written vision pipeline counts pips on a white d6, and the result comes back to Foundry via `window.postMessage` and is posted as a chat message.

Three problems matter more than everything else:

1. **The transport cannot reach a phone.** `postMessage` to `window.opener` only works when the web app is a popup of the Foundry tab on the same device. The project goal ("phone or webcam") needs a cross-device channel, and that choice shapes pairing, security and hosting. It should be decided before more is built on the popup model.
2. **Results don't enter Foundry's dice system.** The module posts an HTML chat line. Nothing creates a `Roll`, so game systems, attack/damage workflows, Dice So Nice and roll modes never see the result. Foundry v12+ ships a built-in hook for exactly this: dice fulfillment methods (`CONFIG.Dice.fulfillment.methods`, `RollResolver`, `Roll.registerResult`). Using it inverts the flow: Foundry asks for "2d6" from the system's own roll, and the camera fills it in.
3. **The vision code has no measurement.** `vision.ts` is ~1,700 lines of hand-tuned heuristics (five die-candidate strategies, retry crops, ~130 numeric constants) with no committed fixtures and no automated accuracy test. Every tweak is judged by eye in the browser. It will be impossible to tell whether a change helps or regresses, and the approach does not extend to numeral dice (d20) on the roadmap.

## Findings

### Architecture

| # | Finding | Evidence | Severity |
|---|---|---|---|
| A1 | Same-device-only transport (`window.opener.postMessage`). Phone use is impossible. | `apps/web/src/App.tsx` `sendConfirmedRoll`; `apps/foundry-module/src/index.ts` `registerWindowBridge` | High |
| A2 | Camera on a phone requires a secure context (HTTPS). The plan assumes a Vite dev server, which is plain HTTP on the LAN, so `getUserMedia` will be blocked on phones. Hosting is unplanned. | `apps/web/vite.config.ts`, `DEFAULT_WEB_APP_URL = "http://localhost:5173"` | High |
| A3 | Results are chat text, not Rolls. No integration with Foundry's dice fulfillment API, game systems, roll modes, or Dice So Nice. | `handleExternalRoll` → `ChatMessage.create({ content })` | High |
| A4 | Push model: the camera decides what was rolled and how many dice. Foundry should own the formula (how many dice, which kinds) and the camera only answers it. | Spec §4, §6 | Medium |
| A5 | `module.json` pins Foundry 13 only; v14 is current. | `apps/foundry-module/module.json` | Low |

### Contracts and trust

| # | Finding | Evidence | Severity |
|---|---|---|---|
| C1 | Payload validation checks types only: a d6 value of `7`, `NaN`, or a `total` that doesn't match the dice is accepted. | `isExternalRollPayload` in `packages/shared/src/contracts.ts` | Medium |
| C2 | Session id is deterministic (`dicewatcher-<userId>`) and there is no secret, so "pairing" is not authentication. Fine for postMessage (origin check does the work), but unusable once a network transport exists. | `getSessionDetails` | Medium |
| C3 | The web app sends real rolls through `createMockExternalRoll`, so recognition confidence is always reported as `1`. | `sendConfirmedRoll` | Medium |
| C4 | `postMessage` falls back to target origin `"*"` when `foundryOrigin` is missing from the URL. | `sendConfirmedRoll` | Low |
| C5 | Spec calls for Zod; the code uses hand-written guards. Pick one; Zod (or Valibot) gives range checks for C1 for free. | spec §5.2 vs `contracts.ts` | Low |

### Vision

| # | Finding | Evidence | Severity |
|---|---|---|---|
| V1 | No labeled fixture set in the repo and no automated accuracy test. The batch/fixture tools live in the product UI and export results by hand. | `App.tsx` fixture/batch sections; no `fixtures/` dir | High |
| V2 | Recognizer depends on the DOM (`document.createElement("canvas")`, `Image`) so it cannot run in Node/Vitest. The core should be a pure function over `ImageData`-like pixels. | `recognizeD6FromDataUrl`, `loadImage` | Medium |
| V3 | Heuristic sprawl: five candidate finders + retry crop + layout scoring with ~130 tuned constants, tuned on one white d6. Likely overfit; doesn't extend to d20 or multiple dice. | `vision.ts` | Medium |
| V4 | Runs on the main thread. Fine for one still, a problem for live/auto-capture. Move to a Web Worker. | `vision.ts` | Low |

### Codebase hygiene

|---|---|---|---|
| H1 | No tests, linter, formatter or CI. | repo root | Medium |
| H2 | `App.tsx` is a 950-line component mixing product flow with developer fixture tooling. Split into a camera/review flow and a separate dev bench route. | `apps/web/src/App.tsx` | Low |

| H4 | Build output (`apps/foundry-module/package/`) is committed; README links to a local Windows path; versions disagree (web `0.2.0`, others `0.1.0`); `debugLogging` defaults to on. | various | Low |

## What's good

- The two-app split (camera web app + thin Foundry module + shared contracts) is the right shape and should be kept.
- "Foundry does no computer vision" is the right boundary.
- Confirm/correct before send is the right MVP safety net.
- The spec's instinct to prove the bridge with mock data before CV was correct; the review just found the bridge was proven on a transport that can't carry the real use case.
- The pip pipeline does work on its target case, and its debug image/notes output is a good foundation for a measurement harness.
